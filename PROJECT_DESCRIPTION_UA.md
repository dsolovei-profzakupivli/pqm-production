# Prozakuplivli Qualification Manager (PQM)

## Призначення

PQM — локальний прототип робочого середовища для супроводу кваліфікації постачальників Prozorro Market. Система об'єднує заявки, кваліфікації, відбори, закупівлі, перевірочні реєстри та внутрішні рішення УО в одному інтерфейсі.

## Основні модулі

### Реєстр заявок

- пошук і комбіновані фільтри за постачальником, кодом, статусом, відбором, датою та профілем;
- перегляд документів заявки й документів рішення;
- внутрішні поля комплаєнсу, рішення УО, протоколу та дії на майданчику;
- масове заповнення;
- контроль обов'язкових полів і блокування несумісних рішень;
- формування DOCX-протоколів;
- журнал внесених змін.

### База постачальників

- агрегована картка кожного постачальника;
- повна та скорочена назва з ЄДР, ПІБ керівника і статус у ЄДР;
- статистика активних та неактивних кваліфікацій;
- кваліфікації за відборами з датою останньої дії;
- участі та перемоги у закупівлях;
- звернення замовників і результати їх розгляду;
- маркери та історія АМКУ/НАЗК;
- переходи між реєстрами, відборами та карткою постачальника.

### Відбори

- перелік відборів із кодом ДК, Agreement ID, категорією, статусом і строками;
- групована статистика постачальників: кваліфіковані, з пропозиціями, учасники поточного року, без участі;
- статистика закупівель: оголошено, успішні, неуспішні, Bids і остання закупівля;
- детальна картка відбору зі складом постачальників, участями, перемогами та маркерами АМКУ/НАЗК.

### Закупівлі за відборами / Bids

- стан локальної історичної бази ProzorroBids;
- ручне оновлення та індикація охопленого періоду;
- постійний набір для Power BI без накопичення дубльованих експортів.

### Довідники

- реєстр НАЗК із пошуком, датами й органами;
- реєстр АМКУ з пошуком, датами, органами та виділенням постачальників PQM;
- конструктор типових зауважень;
- ручна синхронізація контрольних Google-таблиць через OAuth у режимі лише читання.

### Звернення замовників

- реєстр звернень;
- підстави, статуси, рішення та документи;
- зв'язок із карткою відповідного постачальника.

## Логіка контрольних маркерів

- Запис АМКУ виділяється як поточний ризик лише за наявності актуальної активної кваліфікації у чинному відборі. Кваліфікації завершених або прострочених відборів активними не вважаються.
- Підтверджений запис НАЗК є поточним маркером лише тоді, коли перевірений ПІБ збігається з чинним керівником за ЄДР. Після зміни керівника попередня перевірка зберігається як історична інформація.
- Різні статуси Prozorro, ЄДР, АМКУ та НАЗК не змішуються й відображаються окремо.

## Архітектура контрольної версії

- Python 3.12, локальний HTTP-сервер;
- SQLite — основна локальна база;
- HTML, CSS і JavaScript без окремого frontend-фреймворку;
- інтеграції з Prozorro API та Google Sheets API;
- окрема зовнішня SQLite-база ProzorroBids для великої історичної аналітики.

## Статус

Це тестова локальна версія для перевірки логіки та інтерфейсу. Вона не є розгорнутою промисловою вебсистемою. Перед продуктивним використанням потрібні серверне розгортання, централізована автентифікація, розподіл ролей, резервне копіювання, захист секретів, аудит безпеки та міграція лише погоджених налаштувань і довідників без перенесення тестових ручних рішень.
